# Real-data check 1: projection and the multi-LiDAR chain on A2D2

This check runs the engine on real sensor geometry from A2D2. It feeds the
same LiDAR points to the engine in two ways and compares the engine's pixel
and depth for each point with the values A2D2 stores.

- **Direct:** the points already registered to the front-centre camera, as
  one scan with identity extrinsics.
- **Chain:** the same points moved back into each of the five source
  LiDARs' own frames, one scan per LiDAR. Each scan comes with that LiDAR's
  extrinsics to the camera, built through the vehicle frame.

Tooling: [`tools/datasets/a2d2/`](../../tools/datasets/a2d2/). It is Python 3
with numpy only, pinned in `requirements.txt`, and it sits outside the C++
libraries.

## What it proves

- **Conventions.** The engine's optical frame (x right, y down, z forward)
  and its pixel-centre convention (pixel centres at integer coordinates,
  image spanning `[-0.5, W - 0.5)`) agree with A2D2's projection. All
  866,142 points agree to within 1.1e-4 px. None is visible to the engine but
  outside the image for A2D2, and none the other way round.
- **Intrinsics handling.** `CamMatrix` goes into the sensor config unchanged
  with zero distortion, which is right for A2D2's undistorted images. The
  engine reproduces A2D2's `col`/`row` exactly, apart from float32 point
  storage.
- **Extrinsic chain arithmetic.** For each LiDAR,
  `T_camera_lidar = T_camera_vehicle · T_vehicle_lidar` is parsed from
  YAML, re-orthonormalised and applied by the engine. The check covers
  five real mounts. Their rotations relative to the vehicle range from 24°
  to 179°, and their z-axes are tilted 11° to 37° from vertical. The
  result agrees with the direct variant to within 1.9e-4 px and 7.6e-6 m.
- **Multi-LiDAR merge.** The per-LiDAR outputs, put back together and
  z-buffered with the engine's rule, give the same visibility and the same
  `nearest` flag for every point as the single direct scan.
- **The A2D2 view convention**, derived from `cams_lidars.json` and
  confirmed against an independent attribute (see below).

## What it does not prove

- **Calibration accuracy.** A2D2's points are already registered to the
  camera using the same `cams_lidars.json` views. Moving them back into the
  LiDAR frames and forward again is a closed loop: it checks the engine's
  arithmetic and conventions, not whether the views match the real sensor
  mounting. An error in A2D2's calibration would not show up here.
- **Time alignment and motion compensation.** The LiDAR scans get the
  camera's own timestamp and there is no trajectory, so association is
  trivial (`delta_t = 0`) and nothing is compensated. A2D2's per-point
  `timestamp` is about 37 s away from `cam_tstamp` in this drive, and
  `tstamp_delay` is not used.
- **Lens distortion.** The images are undistorted, so the distortion model
  is not exercised.
- **The z-buffer against image content.** Occlusion is judged only among
  the LiDAR points themselves.
- **The chain inside the engine.** The sequence format has one LiDAR per
  sequence and one `T_camera_lidar` per camera. The two-step composition is
  therefore done in float64 by the converter, and the engine applies the
  composed transform. Each LiDAR runs as its own sequence, and the
  cross-LiDAR z-buffer is computed by `compare.py` from the engine's output
  using the engine's rule. It is not computed inside the engine.

## The view convention

Each A2D2 sensor has a `view`: an origin and the sensor frame's x- and
y-axes, all in vehicle coordinates. With `z = x × y` and
`R = [x y z]` (axes as columns):

```
p_vehicle = R · p_view + origin            T_vehicle_view = (R, origin)
```

The camera view frame is x forward, y left, z up. The engine's optical frame
is `Q = (-y, -z, x)` of it. So

```
T_camera_vehicle = R_optical_view · T_vehicle_cameraview⁻¹
T_camera_lidar   = T_camera_vehicle · T_vehicle_lidar
p_lidar          = T_vehicle_lidar⁻¹ · T_vehicle_cameraview · p_view   (chain scans)
```

The converter checks this convention numerically on all 50 frames.

- It moves each point into its source LiDAR's frame and compares
  `π/2 − atan2(y, x)` with A2D2's per-point `azimuth`. A Velodyne measures
  azimuth clockwise from its y-axis. The median residual is 0.14° to 0.24°
  for each of the five LiDARs.
- With the transposed convention (axes as rows) the median residual is
  175.7° for `front_center`, 12.1° for `front_left` and 5.3° for
  `rear_left`.
- For `front_right` and `rear_right` the two conventions are hard to tell
  apart (3.1° and 0.2°), because those mounts are rotated by about 179°.
  Such a rotation matrix is almost symmetric, so its transpose is nearly the
  same matrix.
- Elevation angles in the correct frame also fall into far fewer
  0.1° bins (the laser rings): 153 to 232 bins against 211 to 593 for the
  transposed convention.

The stored `col`/`row` equal the `CamMatrix` projection of `Q` (median
5.7e-14 px, max 5.1e-13 px over all points).

## Results (50 frames, 866,142 points)

Run on 2026-11-03 with a `default` (GCC, RelWithDebInfo) build of
`fuse_cli`. Pixel error is the distance between the engine's `(u, v)` and
A2D2's `(col, row)`. Depth error is `|engine depth − A2D2 depth|`.

| variant | compared | median px | max px | within 0.5 px | median depth | max depth |
|---------|----------|-----------|--------|---------------|--------------|-----------|
| direct  | 866,142 of 866,142 | 1.6e-05 | 1.1e-04 | 100% | 3.2e-07 m | 3.8e-06 m |
| chain   | 866,142 of 866,142 | 1.4e-05 | 1.1e-04 | 100% | 3.2e-07 m | 4.0e-06 m |

Per LiDAR (chain), max pixel error / max depth error:

| lidar        | points  | max px   | max depth  |
|--------------|---------|----------|------------|
| front_center | 262,121 | 1.04e-04 | 3.87e-06 m |
| front_left   | 237,146 | 1.06e-04 | 3.83e-06 m |
| front_right  | 200,324 | 1.14e-04 | 3.81e-06 m |
| rear_left    | 81,241  | 1.05e-04 | 3.95e-06 m |
| rear_right   | 85,310  | 1.03e-04 | 3.82e-06 m |

- **Chain vs direct:** at most 1.9e-04 px and 7.6e-06 m apart. No point is
  visible in one variant only, and no `nearest` flag differs between the
  direct run and the merged chain runs.
- **Where the residual comes from.** The sequence format stores points as
  float32. A float64 projection of the same float32 points that the engine
  read differs from the engine's output by at most 5.1e-13 px (direct) and
  1.7e-12 px (chain). So the whole difference from A2D2 is the rounding of
  the points to float32, about 3.8e-6 m at 64 m. Chain and direct round
  different coordinates (LiDAR frame versus camera frame), so their
  difference can reach twice that. Nothing was tuned to get these numbers.
- **Visibility.** A2D2 places all 866,142 points inside the image, and the
  engine projects all of them. The engine hides 5,909 points (0.7%) from
  its depth map because a nearer point lands on the same pixel (the
  z-buffer). A2D2 keeps every point. Those points still have a projection
  in the engine's output and are included in the comparison above. With
  one sequence per LiDAR, the per-LiDAR z-buffers hide 2,669 points; merged
  across LiDARs they hide the same 5,909 as the direct scan.
- **Processing time** (`fuse_cli`, `build_aligned_frame()` only): median
  3.7 ms per frame for the direct scan of about 17,000 points, and 1.5 to
  2.0 ms per single-LiDAR scan. This is one run on one development machine,
  not a benchmark.

## How to reproduce

**1. Data.** The public bucket is
`https://aev-autonomous-driving-dataset.s3.eu-central-1.amazonaws.com/`.
The check used frames `000000060` to `000000109` of drive `20180810_150607`.
The full archives are large: 54 GB for the camera and 15 GB for the LiDAR.
The commands below stream them and keep only those frames. They have not
been run as part of this check, which used a slice that had already been
extracted to `/data`.

```sh
B=https://aev-autonomous-driving-dataset.s3.eu-central-1.amazonaws.com
mkdir -p ~/a2d2 && cd ~/a2d2
curl -O "$B/cams_lidars.json"
for part in camera_frontcenter lidar_frontcenter; do
  curl -s "$B/camera_lidar-20180810150607_$part.tar" | tar -x --wildcards \
    '*_00000006[0-9].*' '*_0000000[7-9][0-9].*' '*_00000010[0-9].*'
done
# -> ~/a2d2/camera_lidar/20180810_150607/{camera,lidar}/cam_front_center/
```

**2. Build `fuse_cli`.**

```sh
cmake --preset default && cmake --build --preset default
```

**3. Convert and compare** (in a virtual environment outside the
repository):

```sh
python3 -m venv ~/a2d2-venv
~/a2d2-venv/bin/pip install -r tools/datasets/a2d2/requirements.txt
~/a2d2-venv/bin/python tools/datasets/a2d2/convert.py \
    --data ~/a2d2/camera_lidar --config ~/a2d2/cams_lidars.json \
    --first 60 --last 109 --out /tmp/a2d2_work
~/a2d2-venv/bin/python tools/datasets/a2d2/compare.py \
    --work /tmp/a2d2_work --fuse-cli build/default/apps/fuse_cli \
    --results /results/a2d2
```

`convert.py` writes the direct sequence, one chain sequence per LiDAR, and
the per-point A2D2 reference (`reference/NNNNNN.csv`: `row`, `col`,
`depth`, `lidar_id`, and the point's index in its LiDAR's chain scan). It
also writes `transforms.json` and `convention_check.json`. The RGB list
files point at the original PNGs by absolute path, so no image is copied.

`compare.py` runs `fuse_cli` on all six sequences. `fuse_cli` keeps the
scan order, so engine points are matched to the reference by index. It then
writes:

| File | Contents |
|------|----------|
| `per_frame_lidar.csv` | per variant, frame and `lidar_id` (plus `all`): count, points inside the image for A2D2, visible to the engine, compared, visibility disagreements both ways, z-buffer hidden (per LiDAR and merged), median and max pixel error, fraction within 0.5 px, median and max depth error |
| `chain_vs_direct.csv` | per frame and `lidar_id`: max and median pixel difference, max depth difference, visibility and `nearest` disagreements |
| `summary.json` | totals over all frames, chain vs direct, the convention check, `fuse_cli` median processing time |
| `report.md` | the same as short tables |
